# M25 — Performance, portability and project durability

**Status:** Portable implementation, archive integrity tests and cross-platform CI are complete. CI passes on Python 3.10, 3.11, 3.12 and Windows; the 5-second 48 kHz archive/export/reopen smoke passes in all four jobs (Windows regression: 307 tests passed). The 30-second/180-second target-Windows run, declared target memory/time budget, Pyo-enabled audition and human listening sign-off remain open. See [CI run 45701978735](https://github.com/ilyaminineli/eli_lab-reawarp/actions/runs/45701978735).
**Depends on:** M14 performance baseline; M18 typed control/provenance; M21 source and processing identity; M22 routing/tail/latency contracts; M23 candidate ancestry; M24 DSP research module provenance.

## Goal

Make long-form work measurable and recoverable, and make an exported project a self-describing archive rather than a folder of WAVs plus undocumented local paths. Reproducibility statements distinguish an exact archived artifact from a regenerated render.

## Delivered implementation

### 1. Target-machine benchmark and sign-off harness

`scripts/benchmark_m25.py` runs the canonical engine, exports a portable project, reopens it and audits its asset and file hashes. Its default target cases are 30 seconds and 180 seconds at 48 kHz. It records:

- OS/release, processor, architecture, physical RAM, Python implementation/version, NumPy and SciPy versions.
- Full generation configuration, seed, sample rate, duration, frames, stem and event counts.
- Planning, composition planning, event generation, sample preparation, voice-renderer setup, Score control/scheduling, per-voice callbacks, sample-trigger callbacks, event accumulation, field layers, headroom, FX, export and reopen timing.
- Total wall time, generation wall time, real-time factors, sampled peak process RSS, tracemalloc peak, buffer estimates and final archive size.
- Portable asset audit, full project-file integrity audit and optional Pyo integration outcome.

The Score renderer's new timing map is diagnostic only. It does not alter scheduling, callback order, random streams, audio or mix gain.

Run on the target Windows machine:

```powershell
python scripts/benchmark_m25.py --durations 30 180 --sample-rate 48000 --output output/m25-target-windows.json
```

An acceptance run must declare the actual machine budgets rather than accepting an arbitrary default:

```powershell
python scripts/benchmark_m25.py --durations 30 180 --sample-rate 48000 --max-rss-gb <budget-in-GiB> --max-wall-seconds <budget-in-seconds> --output output/m25-target-windows.json
```

For the optional Pyo-backed routing/render path, install the `pyo` extra and add `--pyo`. A failed Pyo render is recorded and causes the benchmark to fail; a run without `--pyo` explicitly reports that integration as not run.

The CI workflow runs a five-second, 48 kHz archive/export/reopen smoke case on Linux and Windows. This proves the pipeline can run in those environments; it is not a substitute for the 30/180-second test on the actual target computer. No target budgets have been supplied or inferred, so the long-run resource gate remains pending until those values and the report are recorded.

### 2. Measured optimisation

The engine now exposes timing detail instead of a single opaque render duration:

- Planning and event generation remain separate.
- Sample-bank preparation, renderer construction, score control-bus creation, event scheduling and voice callback time are separated.
- Callback counts and elapsed time are grouped by voice and event kind; sample-trigger callback time is reported separately.
- Field-layer and headroom passes remain separately timed.
- The M25 harness adds routing/FX, export, archive verification and reopen timing.

The harness records traced Python allocation peak and sampled process RSS. It also reports the size of the stem buffers and exported artifacts. The current renderer still holds whole-project stem arrays in memory; the new measurements make that budget visible rather than claiming it is streaming.

No GPU/native rewrite or speculative cache was added. Optimisation is deliberately evidence-gated: first capture 30/180-second profiles on the target machine, identify a hotspot, then make a bounded change and compare deterministic output, memory, and musical audition against the portable reference. Cache keys must include source identity/hash, processing parameters, algorithm version and sample rate; cache storage must have a size/eviction limit before being enabled.

### 3. Project manifest and asset portability

Every new `ReawarpProject.export()` writes `manifest.json` after the project, Score, events, stems, master and portable assets are present. The manifest has its own schema version 1 and records:

- Application, algorithm/renderer and embedded Project, Score, Event, routing, automation, Sound Object and candidate schema versions.
- Sample rate, frame count, duration, stem names, event count and a canonical configuration hash.
- Root seed, seed streams, generator families, tuning, Score provenance and selected sample-source metadata.
- Candidate ancestry (candidate ID, parent, mode, targets, selection state and variation seed).
- Source assets with stable SHA-256 IDs, file path, file size and all configuration references that consume the asset.
- FX routing/automation/mix sidecar names; the file inventory records their hashes.
- OS, processor, physical memory, Python, NumPy and optional SciPy environment details.
- A reproducibility declaration: archived audio/files have exact SHA-256 identities; same-environment rerendering is a separate comparison; cross-environment regeneration is best-effort and is not promised bit-identical.

Asset policy is explicit:

- `asset_policy="copy"` is the default. Referenced samples are copied to `assets/` and configuration references are rewritten to project-relative paths. The source file remains untouched.
- `asset_policy="reference"` preserves an external absolute path and records its content hash. Use this when the archive must not duplicate a large sample library.
- Missing files are recorded as missing with a stable missing-path ID and the configured path. No replacement sample is selected automatically.
- On load, relative packaged references resolve against the project directory. Source and file-inventory audits report missing and changed assets in project metadata; the load operation never repairs or mutates the archive silently. Legacy v1 projects without a manifest receive a non-mutating audit of the sample paths still present in their config, so an old missing external dependency is not hidden merely because that export predates the manifest.

New desktop exports include the current FX routing and automation sidecars, mix settings, return WAVs, the routed master and a refreshed file inventory. The portable archive service is in `reawarp.export.project_archive`, outside the window class.

### 4. Schema compatibility and archived fixtures

M25 does not force a needless version bump to the existing project file. Current compatibility is:

| Data | Current schema | Read/migration behaviour |
|---|---:|---|
| Project export | 1 | Existing v1 exports continue to load; a manifest is optional for legacy archives |
| Project manifest | 1 | Validated separately; unknown versions raise an actionable migration error |
| Project events | 1 | Validated as part of project reopen |
| Score | 1 | Existing v1 Score loads; unsupported versions are rejected by the Score model |
| FX routing | 3 | v1/v2 migrate in memory to v3; source files are not rewritten |
| FX automation | 1 | v1 loads through the existing validator; unknown versions are rejected |
| Sound Object | 1 | v1 patch validation remains strict |
| M23 candidate record | 1 | The new marker defaults to v1 when reading an archived record without the field |

Archived source fixtures live in `tests/fixtures/m25/legacy_contracts_v1.json`. Regression tests cover loading the old formats, routing migration, explicit unsupported-manifest errors, portable asset copy/reference paths, missing/changed assets, archive re-open, sidecar round-trip and manifest integrity. Migration is in memory; it does not overwrite the source project. An unsupported version is not guessed or coerced: the error names the need for an explicit migration.

The compatibility window policy is conservative: keep the current version readable, retain an explicit tested migration for the previous supported routing versions, and add a fixed archived fixture before accepting each new schema transition. No implicit "best effort" parse of unknown structures is allowed.

### 5. Application boundaries, cancellation and recovery

The M25 pass moves project archive assembly and hashing out of `MainWindow` into `export_project_archive()`. The window now snapshots UI/routing/audio state and submits the work to a cancellable worker; archive logic owns writing, sidecar validation, WAV outputs and the final manifest.

Current service boundaries:

| Concern | Owner | Current boundary |
|---|---|---|
| Project/Score generation | `ReawarpEngine`, Score planners/renderers | Deterministic engine API; cooperative cancellation between planning, render phases and score events |
| Score voice scheduling | `ScoreRenderer` | Frame scheduling, control evaluation, callback invocation and per-voice diagnostics |
| Project archive/load | `ReawarpProject` + `project_archive` | Schema validation, project files, sample packaging, checksums, FX sidecars and reopen |
| FX routing/render | `fx_routing.py` | Non-destructive routing service, tail/return output and existing cancellation checks |
| Variation batches | `VariationBatchService` + cancellable worker | Candidate generation and ancestry independent from widget display |
| Transport | `AudioPlayer` + transport timer | Playback owns audio; UI updates position and stops it during shutdown |
| Desktop coordination | `MainWindow` | Collect input, freeze snapshots, dispatch workers, and present status/results |

The widgets remain responsible for input and presentation. `MainWindow` is still the coordinator for project-session state and the FX render/cache signature; it is not yet a small application shell. The next extraction should be staged: first a ProjectSession (active project, candidate ancestry, routing and automation snapshots), then a generation-job coordinator, then an FX render/cache coordinator. Transport should only be extracted after its device lifecycle and owner-thread rules have separate tests. Do not move all state at once or change render ownership during a schema migration.

Cancellation is cooperative at safe checkpoints: score event scheduling and rendering, engine phase boundaries, project stem/candidate loops, sample packaging/hash blocks, FX routing passes and archive artifact boundaries. A single voice callback or individual WAV write is not interrupted in the middle of its call. Shutdown stops timers and playback, requests cancellation from active render/export/FX/variation workers, clears pending queued work and waits for active jobs before the window exits. Worker errors are surfaced; cancellation does not overwrite the active project or treat a partial export as complete. A cancelled export may leave an incomplete destination folder; the absence of a refreshed/valid manifest is the recovery signal. Exporting to a new or empty directory is recommended for archival snapshots.

## Not in scope

Speculative GPU acceleration; native rewrites without benchmark evidence; cross-platform bit-identical promises; automatic substitution of missing samples; silent schema coercion; general-purpose plug-in management; or a wholesale UI/controller rewrite without incremental service contracts and tests.

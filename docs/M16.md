# M16 — Score-driven render core

**Status:** The score-native renderer, shared musical clock, typed automation control bus, score provenance, planner adapters, production synthesis callbacks and scheduled sample/break callbacks are implemented. The legacy `generate()` pipeline remains available but has not yet been cut over to canonical score-first rendering.

## Goal

Make the universal score the canonical symbolic event representation consumed by an offline render core. Rational beat values remain exact until a score event is resolved onto a sample frame.

## Delivered in this increment

### 1. Shared render timeline

RenderTimeline centralises:

- rational beat to seconds conversion through TempoMap;
- beat to sample-frame conversion with deterministic nearest-frame rounding (ties round upward);
- frame to seconds and frame to rational-beat conversion;
- meter lookup and bar/beat queries through MeterMap;
- event start/end frame calculation, including tempo changes inside a note.

The tempo map integrates 60 divided by BPM over beat position. A linear BPM ramp is not approximated as a linear elapsed-time ramp. A meter change begins a new bar according to the existing MeterMap rules; pattern cycle lengths remain independent.

### 2. Score-native offline rendering

ScoreRenderer.render(score, sample_rate, ...) schedules Score.events and renders each voice into a separate dry stereo stem. Event onset and end frames are derived only from the score and its tempo map. Notes, hits, grains, and triggers are renderable; control and marker events remain symbolic.

The renderer provides a deterministic reference voice for basic note and transient audition. Applications can inject per-voice callbacks for production subtractive/FM/sample renderers. A callback receives the scheduled score event, render sample rate, and shared AutomationControlBus; it returns a mono or stereo float buffer with exactly the scheduled event length. Velocity, mono equal-power panning, frame placement, and finite-buffer validation are handled by the score renderer.

The reference voice is deliberately modest; it does not replace the M8–M15 instrument palette with one generic oscillator. It establishes the renderer contract so specialist production voices can be adapted one lane at a time.

### 3. Typed automation and one control clock

AutomationTargetRegistry defines target domain, units, value type, bounds, and supported interpolation modes. The default registry covers synthesis cutoff, resonance, gain and pitch; FX insert wet, SPACE/ECHO sends and shared return wet; and MIDI CC destinations, validated from channel/controller IDs.

AutomationControlBus evaluates beat-, second-, and frame-based lanes at absolute render frames. Frame-based lanes retain their source sample-rate reference when rendering at a different sample rate. Synthesis callbacks and downstream FX processors can request values or fixed-rate control samples from the same bus, avoiding independent beat/seconds conversions.

M17.4 connects the existing M13 role-aware FX automation file to this typed model. M13 targets retain their established IDs (`bus.space.wet`, `bus.echo.wet`, and the per-stem insert/send IDs); its version-1 JSON schema remains unchanged. The point-level `hold`, `linear`, and `smooth` curve is stored on `AutomationPoint.interpolation_to_next`, so a lane may mix different segment curves without flattening. Smooth uses the original smoothstep function. Pre-first-point values continue to come from the static routing defaults.

Use `ReawarpEngine.render_score(score, fx_automation=legacy_payload)` to attach legacy M13 automation before score rendering. The resulting `ScoreRenderResult.controls` is the shared automation source for production voices and the downstream FX router:

```python
rendered = ReawarpEngine().render_score(score, fx_automation=fx_automation_json)
processed, fx_metadata = render_fx_routing(
    rendered.stems, rendered.sample_rate, routing,
    controls=rendered.controls,
)
```

The FX router evaluates score controls on the same absolute frame/tempo-map clock (sampled at 1 kHz for FX gain envelopes, then interpolated to audio frames). Existing callers may continue using `render_fx_routing(..., automation=legacy_payload)`; supplying both legacy JSON and a score control bus is rejected to avoid ambiguous precedence. `score_to_fx_automation(score)` projects compatible typed lanes back to M13 schema v1.

Custom targets remain supported through an explicit custom-target allowance. Strict registry validation rejects unknown targets, unit mismatches, out-of-range values, unsupported interpolation, and invalid MIDI CC addresses.

### 4. Project and provenance

ReawarpProject.export() continues writing the full project, aligned dry WAV stems, event records, and canonical score.json. Project metadata records the renderer version and a render-provenance record. Project-derived scores record score-renderer version, source generator version, root seed, sample rate, frame count, duration, named seed streams, and generator-family provenance.

Existing project schema and score schema version 1 remain readable. Old exports without M16 provenance fields continue to load; no stem is silently reconstructed from a score.

### 5. MIDI 1.0 representational limits

MIDI remains an interchange adapter, not the canonical render format:

- MIDI 1.0 note numbers are integer semitones; fractional pitch and exact frequency survive only in Reawarp text metadata.
- MIDI time is a finite ticks-per-beat grid. Reawarp rounds rational event positions to the nearest MIDI tick at the selected PPQ.
- MIDI tempo events are discrete microsecond-per-quarter-note values. Linear BPM ramps are sampled into tempo events at the requested export resolution; import therefore reconstructs a step map, not the original continuous ramp.
- MIDI time signatures are discrete conductor events. Reawarp rational score time and meter rules are richer than the MIDI conductor grid.
- Generic synthesis/FX automation is not natively portable in MIDI 1.0. MIDI CC lanes map to CC messages; additional Reawarp automation and event metadata rely on text meta events that other applications may strip.

## API

    from reawarp import ReawarpEngine, Score
    score = Score.load("output/my-composition/score.json")
    rendered = ReawarpEngine().render_score(score, sample_rate=48_000)

    rendered.stems       # dry stereo buffers keyed by voice_id
    rendered.render_master()
    rendered.schedule    # event IDs, sample frames, bars, and beat offsets
    rendered.controls    # shared frame-addressed automation bus for synth and FX

A production voice can be injected per voice:

    def lead_voice(scheduled, sample_rate, controls):
        cutoff = controls.sample(
            "synth.cutoff", scheduled.start_frame, scheduled.end_frame,
            step_frames=max(1, sample_rate // 1000),
        )
        return my_synth(scheduled.event, sample_rate, cutoff.values)

    result = ReawarpEngine().render_score(
        score, sample_rate=48_000, voice_renderers={"lead": lead_voice}
    )

## Compatibility boundary and remaining work

The existing Generator remains available and deterministic. M17.1 added planner-level adapters that construct canonical score events from the percussion sixteenth grid and melody grid positions. Melody score events now distinguish the note gate from the scheduled release span; percussion score spans encode the selected role's default production duration. The legacy `generate()` path still constructs and renders its established MelodyEvent/PercussionEvent records, so end-to-end generation has not yet migrated.

M17.2 adds `reawarp.synthesis.score_voices.build_production_voice_renderers()`. It adapts the existing subtractive, FM/hybrid and extended melody voices, role-specific kick/snare/hat profiles, and synthetic break voices to the `ScheduledScoreEvent` callback contract. Each event gets a deterministic event-derived NumPy RNG, independent of callback order. The production callbacks consume the shared AutomationControlBus for synthesis gain and cutoff/resonance shaping, with pitch automation sampled at note onset. The score renderer still owns velocity, panning, frame placement and output validation.

A production score can be auditioned with:

    from reawarp import ReawarpEngine, GenerationConfig, Score

    score = Score.load("output/my-composition/score.json")
    rendered = ReawarpEngine().render_score(
        score, config=GenerationConfig(synth_palette="subtractive")
    )

Callers may continue to supply explicit `voice_renderers`; passing both custom callbacks and a production config is rejected. When a production config is supplied, `render_score()` also calls `synthesis.score_samples.prepare_score_sample_renderers()` and composes sample callbacks with the existing synthesis callbacks. The sample triggers use the same voice IDs as their hit/body events, but have distinct score event IDs and `kind="trigger"`. The score renderer therefore schedules and mixes the sample transient and synthesis body independently on the same musical onset. The `percussion_synthesis="samples"` setting still selects the legacy profiled drum synthesis voice; only `percussion_source_mode="sample"` suppresses the synthesis hit and plays the imported sample as the source.

M17.3 adds:

- role banks loaded from `sample_banks` or single `sample_paths`, retaining asset IDs, labels, hashes, features and complete provider/IRO metadata;
- explicit sample-trigger events whose asset choice, phrase function, section index, cycle index and source gains are persisted on the score;
- deterministic anchor/return recall and feature-guided sample variant selection at section/cycle boundaries using the existing selection algorithm and independent derived seeds;
- transient/body and layered sample architectures with sample playback duration resolved from score time to the exact scheduled frame span;
- feature-guided synthesis voice, pitch-ratio and velocity adaptation carried onto the base hit event;
- imported break transforms and transient slicing, with each slice bounded by the next trigger or current bar boundary, then trimmed and edge-faded on the absolute render frame clock.

The prepared score also stores a `sample_schedule` manifest with bank variants, source hashes, provider metadata, switch points and per-variant usage. Missing imported assets fail with a path-specific error rather than silently substituting another sound.

The legacy `generate()` pipeline still uses its existing event loop and remains unchanged by this score-render adapter work. Existing project exports and config schemas remain readable.

Remaining M17 integration work:

1. cut generation over so the canonical Score is produced before audio rendering, with project event dictionaries maintained only as compatibility/export views.

Automated tests validate deterministic scheduling, score voice callback output, selected synthesis palettes, role-specific percussion, score-bus controls, tempo conversion, meter changes, automation validation and provenance. They do not establish subjective musical quality or target-machine performance; listening and RTX 4060 profiling remain separate sign-offs.

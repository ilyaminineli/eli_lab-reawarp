# M13 — Musical FX automation and tempo-synchronised motion

## Intent

M13 adds controlled motion to M12 routing without introducing a live-random modulation engine. Insert wet, per-stem send levels, and shared return wet can change at defined musical beats. The Echo bus can lock its delay to a rhythmic division of the project's BPM.

The design follows the IDM guides' recommendations to treat automation as a compositional event, develop one variable at a time, preserve negative space, and distinguish foreground from background. A lane is a deterministic score of control points, not a stream of random values.

## What can be automated

Automation JSON schema version 1 supports these targets:

| Target form | Function |
|---|---|
| `stem.<stem_name>.insert_wet` | Blend the stem's processed insert against its dry source |
| `stem.<stem_name>.send.space` | Animate the stem's send to the shared SPACE bus |
| `stem.<stem_name>.send.echo` | Animate the stem's send to the shared ECHO bus |
| `bus.space.wet` | Animate the SPACE return's wet/dry level |
| `bus.echo.wet` | Animate the ECHO return's wet/dry level |

All values are normalised from 0 to 1. A target without an automation lane continues to use its static M12 routing value. Automation does not change synthesis events, source stems, or named random streams.

## Musical time and interpolation

Point positions use **beats**, not seconds. Frames are derived from the project's constant BPM and sample rate. The current milestone does not add a tempo map; all automation and delay divisions follow the project's single BPM value.

Each point stores:

- `beat`: non-negative beat position
- `value`: control value between 0 and 1
- `curve`: interpolation from this point to the next

Three segment shapes are supported:

- `hold`: retain the point's value until the next point
- `linear`: straight interpolation
- `smooth`: smoothstep interpolation, with a softer start and finish

Before the first point, the static routing value remains in effect. After the final point, its value is held. Points must be strictly ordered and each lane is limited to 128 points. The same input and project tempo always produce the same sample-frame envelope.

## Portable automation JSON

A minimal example:

```json
{
  "schema_version": 1,
  "lanes": {
    "stem.melody.send.space": [
      {"beat": 0, "value": 0.02, "curve": "linear"},
      {"beat": 16, "value": 0.12, "curve": "smooth"},
      {"beat": 32, "value": 0.04, "curve": "hold"}
    ],
    "stem.hats.send.echo": [
      {"beat": 0, "value": 0.00, "curve": "hold"},
      {"beat": 24, "value": 0.05, "curve": "linear"}
    ],
    "bus.space.wet": [
      {"beat": 0, "value": 0.12, "curve": "smooth"},
      {"beat": 32, "value": 0.18, "curve": "hold"}
    ]
  }
}
```

Only current project stem names are accepted. Unknown targets, invalid values, duplicate or unordered beat positions, too many points, and unsupported schema versions are rejected. Existing M12 projects with no automation file continue to render from static routing.

## Tempo-synchronised Echo

The ECHO bus adds a delay-division selector. Supported divisions are:

- 1/2 note
- 1/4 note
- dotted 1/8
- 1/8 note
- 1/8 triplet
- 1/16 note
- 1/16 triplet
- 1/32 note
- static (use the preset's own delay time)

The selected division is converted to seconds from the current project BPM before the offline bus render. This uses the selected bus preset's existing delay stage; selecting a division on a preset without a delay stage is rejected rather than silently ignored.

## Desktop workflow

1. Generate a project and open **STEM MIXER**.
2. The FX workspace has separate **ROUTING** and **AUTOMATION** sub-tabs.
3. In ROUTING, assign static per-stem inserts/sends and choose the ECHO delay division.
4. In AUTOMATION, choose a target, add control points in beats, set values and interpolation, then update or remove points.
5. Save/load the portable automation JSON independently of routing JSON.
6. Audition the master and individual stems. Changing an automation point invalidates the offline FX cache.
7. Export. The project contains dry stems, `fx_routing.json`, `fx_automation.json`, shared return WAVs, routed master, and render/mix metadata.

## CLI workflow

Validate routing and automation without requiring Pyo:

```powershell
reawarp-routing output/my-composition --routing my-routing.json --automation my-automation.json --validate
```

Render the routed project using the project's BPM:

```powershell
reawarp-routing output/my-composition --routing my-routing.json --automation my-automation.json --output output/m13-render
```

The command reads the BPM from `project.json`, applies automation offline, and writes processed stem copies, return WAVs, master WAV, portable routing and automation JSON, and `render.json` provenance. Source files are not overwritten.

## Role-combination audition exports

Generate four comparable mixes from the same exported project without writing a routing file by hand:

```powershell
reawarp-routing output/my-composition --audition-matrix --output output/role-auditions
```

The command creates separate folders for percussion focus, melody foreground, ambience background, and combined roles. Each folder contains processed stem copies, SPACE/ECHO return WAVs, a master WAV, routing JSON, automation JSON, and render metadata. The top-level `audition_report.json` records direct RMS, return RMS, return-to-direct RMS ratio, peaks, and rendered duration for each mix.

Role names are inferred conservatively from generated stem names. Unknown roles remain dry. These are restrained starting configurations for listening comparison, not a claim that the combinations have been subjectively approved. The RMS ratio can flag a return that is numerically too prominent, but it cannot identify masking or decide whether the spatial relationship is musically useful.

## M12 refinement included in this milestone branch

- Routing remains a deliberately small two-bus system (SPACE and ECHO).
- External chain-file path references were removed; custom ordered stages must be embedded in portable routing JSON.
- Insert tails are no longer discarded before shared sends. Direct stem files remain aligned; insert tails can contribute to the send path, and shared returns can extend the master.
- Static bypassed inserts are skipped and do not attempt to initialise Pyo.

## Validation

The smoke workflow checks:

- compile, generator CLI, existing FX chain validation, and local library CLI
- routing JSON normalisation and dry-source immutability without Pyo
- automation schema validation, save/load round-trip, and deterministic hold/linear/smooth envelopes
- routing CLI validation with automation
- offscreen UI construction for the routing and automation editors

No unit-test suite is reintroduced. These checks establish data and control-flow correctness, not the subjective sound of Pyo's effects.

## Listening evaluation still required

The M12 role matrix in [M12.md](M12.md) gives restrained starting points for percussion, melody, ambience, and combined roles. The M13 automation lanes can create controlled entrances, phrase-end release, and shared-room growth. Actual Pyo output still needs listening evaluation on the target Windows audio setup, including low-volume and mono checks. A successful CI run is not an audition.

## Deferred

- Tempo maps and automation points expressed in bars/sections across changing meter
- Direct Pyo parameter automation inside the effect graph (filter cutoff, feedback, size, and modulation depth)
- Async rendering and per-stem/bus incremental cache invalidation
- Sidechain envelopes and cross-stem detector routing
- Arbitrary user bus graphs and parallel insert branches
- Master-bus insert chain, loudness meter, and true-peak analysis
- Automation import/export as MIDI CC or the universal score's automation-event type


## M22 routing and automation integration

M13 schema-v1 automation lanes remain portable and are not rewritten by M22. M22 routing schema v2 can be controlled by the same legacy automation adapter or the typed Score AutomationControlBus. Insert wet, each stem send and SPACE/ECHO return wet keep their existing target IDs; routing schema v1 files migrate to v2 independently. See [M22 — Mixer and routing quality](M22.md) for send tap, return, meter and async preview/export semantics.

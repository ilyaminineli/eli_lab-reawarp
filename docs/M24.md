# M24 — Advanced DSP research modules

**Status:** Active research track. M24.1 has a portable NumPy reference implementation and passes CI on Python 3.10, 3.11, 3.12 and Windows. M24.2–M24.4 now have isolated NumPy reference implementations, local regression tests, benchmarks and audition generators; cross-platform CI and human listening/target-machine profiling gates are evaluated independently. Human listening sign-off remains open for M24.1–M24.4. M24.5–M24.7 remain planned; no module is enabled in the production mixer.

**Depends on:** M21 sound-object contracts and M22 mixer/tail/latency semantics.

## Goal

Introduce advanced DSP as independently scoped optional instruments and processors. The work is deliberately not a combined DSP release. Each module receives its own specification, implementation, reference fixtures, benchmark, acceptance review and listening decision before the next one is allowed to depend on it.

The sound-design guide treats effects as transformations and sound behaviours, not a list of presets. It specifically calls out convolution as a way to make a transient excite a room, object, circuit or designed resonator, and it recommends listening in musical context rather than treating spectral measurements as taste. See sections 20–21 and 54–61 of the sound-design guide.

## Module gate and sequence

| Module | Status | Independent scope |
|---|---|---|
| **M24.1 Convolution and designed IR instruments** | Reference implementation and cross-platform CI passed; human listening sign-off open | Portable FIR convolution, designed modal responses, IR provenance and tail/headroom reports |
| **M24.2 Spectral delay** | Reference implementation + local tests; CI/listening/profile gates open | Frequency-dependent delay, bin/region movement, bounded spectral feedback and attack-aware repeats |
| **M24.3 Cross-synthesis and frequency transformation** | Separate reference algorithms + local tests; CI/listening/profile gates open | Ring modulation, fixed-Hz frequency shift, spectral-envelope transfer and band vocoder |
| **M24.4 Oversampled nonlinear processing** | Reference implementation + local tests; CI/listening/profile gates open | Explicit transfer curves and 1x/2x/4x/8x Kaiser-sinc oversampling |
| **M24.5 Sidechain and envelope routing** | Planned | Detector filtering, envelope extraction, smoothing, hysteresis and explicit cross-stem control |
| **M24.6 Feedback networks** | Planned | Bounded feedback delay networks and resonant recursive structures |
| **M24.7 Optional parallel processing branches** | Research gate only | Add only when an accepted module and a measured musical use-case require a parallel path |

Each module is reviewed on its own. A module can remain experimental or be rejected without blocking the others. A later module must not silently import an unaccepted algorithm.

## Required module specification

Every module document must state:

1. Musical purpose and a representative arrangement use-case.
2. Algorithm and portable reference implementation, including parameter units and ranges.
3. Sample-rate policy, block/partition model and optional oversampling policy.
4. Latency, alignment, tail and (where applicable) feedback-stability policy.
5. CPU, memory and output-buffer budget, with a reproducible benchmark harness.
6. Deterministic random-stream policy and the limits of cross-environment reproducibility.
7. Headroom, denormal, finite-output and mono/stereo compatibility handling.
8. Optional dependencies, native runtime and licensing/source-provenance review.
9. Versioned portable schema, exact bypass behaviour and regression/reference fixtures.
10. A matched-level listening example that identifies a real compositional use. If listening does not support the use-case, the module remains experimental regardless of test results.

## Architecture rules

- DSP research modules live behind independent APIs. They do not become mixer defaults merely because they exist.
- NumPy remains the mandatory reference environment. Optional acceleration must have a portable baseline and cannot become a mandatory native runtime.
- No GPU work without profiling evidence.
- Do not introduce arbitrary feedback graphs. Recursive modules need bounded, inspectable structures and stability limits.
- Preserve source identity, processing identity, render provenance and non-destructive input ownership in the M21 style.
- Keep M22 routing semantics intact. Any future connection to inserts or returns requires a separate routing-contract proposal and its own latency/tail tests.
- Bypass must be exact-length, non-mutating and must not initialize an optional backend.
- No hidden normalization, auto-gain, limiter or dry-signal duplication. Every gain law must be explicit.
- Analysis outputs are diagnostic prompts, not automatic artistic ratings.

## M24.1 — Convolution and designed impulse-response instruments

See [M24.1](M24.1.md).

The reference implementation is a standalone offline FIR module under \`reawarp.dsp.convolution\`. It includes uniform partitioned overlap-add, deterministic modal IR design, hashed portable IR archives, explicit bypass, tail and latency reporting, benchmark and matched-level listening-example scripts.

**Not integrated into M22:** convolution is not a new default role insert, SPACE/ECHO return or master effect. The M24.1 gate is evaluated independently before any possible routing integration.

## M24.2 — Spectral delay

See [M24.2](M24.2.md). The reference API implements independent frequency-region hop delays, per-band feedback/gain, attack-aware repeat attenuation, a finite feedback ceiling and an explicit tail cap. Exact offline file alignment is reported separately from any real-time latency claim.

## M24.3 — Cross-synthesis and frequency transformation

See [M24.3](M24.3.md). Four distinct APIs are implemented: sample-product ring modulation, fixed-Hz analytic frequency translation, smoothed spectral-envelope transfer with carrier phase retention, and a log-band envelope vocoder. They have separate equations and diagnostics rather than one generic “cross-synth” mode.

## M24.4 — Oversampled nonlinear processing

See [M24.4](M24.4.md). The reference processor supports five named transfer functions and native/2x/4x/8x modes. Oversampled modes use symmetric Kaiser-windowed sinc interpolation and decimation with file-alignment compensation. The finite FIR reduces aliasing; it does not promise complete alias elimination.

## M24.5–M24.7 — Future modules and entry criteria

### M24.5 Sidechain and envelope routing

Use the existing typed Score-control and M22 send/mute/solo contracts as the starting point. Specify detector source, detector filter, attack/release or smoothing law, hysteresis, channel-link law, control-rate update and scope. Keep control identity and audio routing separate. No hidden cross-stem connection is allowed.

### M24.6 Feedback networks

Start with a fixed-size, fixed-topology feedback delay network, not a user graph. Specify matrix structure, delay lengths, damping, feedback norm/stability bound, finite-output protection, tail/decay estimation and worst-case headroom. Include long-run bounded-energy tests.

### M24.7 Optional parallel processing branches

This is not an automatic follow-on. It requires an actual arrangement example where serial processing cannot express the needed relationship, a measured use-case, explicit dry/wet summing law, latency alignment and tests against phase cancellation and level bias. If those conditions are not met, keep the M22 fixed serial insert plus shared-return architecture.

## Acceptance matrix

A module is not marked accepted until the evidence is recorded here and in its own document.

| Evidence | Required outcome |
|---|---|
| Offline render | Finite output; inputs and source assets unchanged |
| Determinism | Exact or clearly scoped best-effort reproducibility |
| Timing | Algorithmic latency, alignment and tail measured |
| Resources | CPU, real-time factor, memory/output bytes reported |
| Safety | Peak/headroom, denormal, mono and stereo cases covered |
| Portability | Schema migration/validation, bypass and dependency policy covered |
| CI | Reference fixture and safety tests pass without optional native runtimes |
| Listening | Matched-level example reviewed in context; human notes retained |

## Not in scope

One all-encompassing DSP release, mandatory third-party DSP dependencies, speculative GPU processing, live plug-in hosting, arbitrary feedback graphs, silent insertion into the M22 role map or an automatic artistic quality score.
